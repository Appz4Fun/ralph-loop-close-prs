## 2024-06-19 - Use concurrent PR state checks
**Learning:** Subprocess calls to the GitHub CLI (`gh`), particularly `gh pr view` to check if a PR is still open, are a significant performance bottleneck when executed sequentially in a loop for multiple PRs (N+1 problem). This happens inside the fan-out supervisor before it decides which PRs to spawn workers for.
**Action:** When performing independent CLI operations over a collection of items, use `concurrent.futures.ThreadPoolExecutor` with `executor.map` to run them concurrently. This reduces total latency to approximately the duration of the slowest single call. Always remember to add a guard clause (`if not items: return []`) before dynamically calculating `max_workers` to prevent `ValueError: max_workers must be greater than 0`.
