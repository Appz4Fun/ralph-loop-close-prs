## 2024-05-18 - Fix N+1 PR state checking bottleneck with concurrency
**Learning:** Checking the state of many PRs sequentially via GitHub CLI (`gh`) in loops like `_filter_to_still_open_prs` and the supervisor sweep introduces a massive performance bottleneck due to cumulative API latency. Subprocesses running the `gh` CLI are quite slow.
**Action:** Used `concurrent.futures.ThreadPoolExecutor` and `executor.map` to run these checks in parallel, significantly speeding up supervisor loops and PR fan-outs. Ensure to capture exceptions in worker functions and handle them sequentially in the main thread to avoid interleaving log messages and breaking the `executor.map` flow. Always add a guard clause for empty lists when calculating `max_workers=min(10, len(items))` to avoid `ValueError`.
